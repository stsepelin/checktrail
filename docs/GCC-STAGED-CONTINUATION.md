# Selected GCC12 hosted continuation

The separate `debian-gcc12-hosted-continuation-v1` development profile preserves
the selected Debian GCC `12.2.0-14+deb12u1` source, image, expanded configuration
and default target graph across stopped checkpoints. The frozen uninterrupted
`dpkg-buildpackage -b -us -uc --jobs=4` profile remains unchanged.

Implemented components are the closed phase planner, failed-attempt ledger,
bounded checkpoint codec and fixed first-phase hosted carrier. The carrier stops
at the genuine configure boundary, captures complete mutable state and verifies
an exact-key service restore against independent local identities. Native
configuration, compression, transport and duration qualification remain required
before a later production-length retry. These components do not close the
original producer, compiler/SDK graph, notices or Gate A.

## Original target boundaries

The original rule pins are checked against the closed producer catalog. Actual
configured variables must be captured in the selected producer environment;
manually authored configuration is only planning data. Every value named by the original `flags_to_pass` is captured as well as its complete name inventory. Generated `debian/rules.parameters` is bound separately from immutable original recipe files, because the original control target may regenerate it. The fixed first-party
`gcc-staged-configuration.mk` target emits the selected variables without
requesting a compiler target. Invoking the original Makefile still executes its
parse-time logic and requires operator-level trust from the reviewed carrier.

The selected sequence is:

1. Original source preparation, `dpkg-source --before-build`, original pre-clean
   and configuration. The carrier must record preparation and pre-clean before
   admitting the configuration checkpoint.
2. `stamps/05-build-stamp`, including its original locale prerequisite and the
   recipe-selected bootstrap target and expanded flags.
3. Each actually selected JIT, NVPTX, GCN and HPPA64 branch. JIT includes the
   original conditional tests and local installation. Selected offload install
   stamps precede the main check, as required by the original recipe.
4. `stamps/06-check-stamp`, preserving the original test commands and outcomes.
5. Full `debian/rules build` re-entry, including the configured architecture and
   independent/documentation dependencies.
6. `dpkg-buildpackage -b -us -uc --jobs=4 -nc`, re-entering normal build/install/
   binary processing and requiring final package, buildinfo and changes evidence.

Internal build stamps live in `debian/rules2`. The fixed `gcc-staged-rules2.sh`
proxy makes that changed entry point explicit. It enters the original outer
`debian/rules` with fixed forwarding targets, retaining its locale unexports,
recursive Make level and original parallel-job forwarding into `rules2`. The operator command plan uses
dpkg target mode to retain its build-environment setup; target mode skips the
normal pre-clean and source-before-build steps. The final `-nc` command also
preserves the restored tree. These semantics are documented in the
[Debian dpkg-buildpackage manual](https://manpages.debian.org/bookworm/dpkg-dev/dpkg-buildpackage.1.en.html).

The controller supplies no replacement language, multilib, bootstrap or compiler
flags. The original `profiledbootstrap-lean` expansion is retained when selected
by the pinned recipe; it is not a controller optimization. No stamp is created
by the checkpoint codec or planner. A phase timeout retains an unobserved native
terminal and consumes the aggregate allowance; it cannot publish a completed
checkpoint or advance the phase. Retry starts from the last completed checkpoint.

A real original command can return zero while capture, physical readback or
transport fails. The separate `retention-failed` attempt preserves that real
integer exit and observed terminal, charges all native elapsed time, and supplies
no completed checkpoint or phase advancement. It cannot be rewritten as a
nonzero native exit or as a successful phase.

## First hosted configure checkpoint

The fixed `gcc-hosted-carrier.py` path admits only the reviewed manual diagnostic
workflow on a public stock Ubuntu 26.04 AMD64 host. It verifies the actual GitHub
source job and tracked first-party commit, the pinned image and original inputs,
and the container's exact environment, goals, mounts and resource limits.
Image admission uses the same raw registry and filesystem identity validator as
input acquisition, including its two pinned Docker ID forms. The setup Node
executable is recorded before `sudo`, then its physical path, bytes and version
are rechecked; sanitized image identity fields are retained before any refusal.
Original source preparation and pre-clean are witnessed explicitly. Configure
then captures all original expanded flags and requires the full retained native
language, multilib, JIT, offload, HPPA64, check and package selection.

The entire native namespace is stopped and removed before physical capture.
HOME, APT, temporary and run state remain backed by the checkpoint tree at their
original container paths. Complete stdout and original phase records are retained
inside that tree. Immutable original inputs remain bound to the closed catalog
and require exact reacquisition when reconstructing another job.

`gcc-hosted-phase0-capacity.py` gives the configure attempt its own finite state,
compressed archive, envelope and shared-write-margin budgets. It reobserves the
complete cache listing and usage immediately before save. The documented free
storage allowance is identified separately from an unavailable configured-policy
endpoint; neither a policy-read failure nor a capacity sample grants native
qualification. No quota setting or unrelated cache entry is changed.

The proposed diagnostic workflow saves one source-specific cache key, moves the
local originals aside, restores without fallback keys, and independently checks
the complete physical source/report/mount state. Root-owned expectations and a
fresh-directory witness prevent old local bytes or cache metadata authenticating
themselves. Actual stored service size is checked against the bounded envelope.
Only a completed service replay can finalize the configure ledger. Failed or
skipped save/restore/replay remains a charged attempt without advancement.

The same six-hour source-job clock covers checkout, preparation, native work,
capture, upload, service download, physical replay and finalization. Configure's
time cap and finalization reserve are explicit in its admission record. Sampling
does not prove an enforced disk quota or physical high-water bound. The later
main bootstrap still requires verified external SDK reconstruction and its own
measured scratch, compression, transport and duration admission.

## Physical checkpoint contract

`gcc-staged-checkpoint.py` captures the entire logical `/build` tree with content
hashes, numeric owners, modes, exact symlink targets, hardlink groups and
nanosecond mtime. Device/inode identities are re-established on restoration;
ctime/atime continuity is not claimed. External hardlink aliases and special
files are refused. Symlink targets are retained as inert data and never followed;
the carrier must separately bind any external target to its original pinned
image/package inventory.

Checkpoint limits bound entries, individual files, logical tree bytes, expanded
tar bytes, manifest bytes, compressed bytes and elapsed time. PAX allocation is
bounded before parsing. Capture rehashes the source after writing and verifies
the archive before atomic publication. Restore validates the entire archive into
a fresh private tree, then physically rehashes that tree before publication.
Atomic no-replace publication preserves a concurrent destination.

Restore requires the predecessor archive SHA-256 supplied independently by the
verified ledger. A receipt inside an untrusted cache cannot authenticate itself,
even when its archive and manifest are mutually consistent. Wrong configuration,
image, package inventory, source epoch, phase, sequence or predecessor refuses
restoration. Failed restore leaves the old checkpoint and any existing target
untouched.

## Carrier admission remains separate

The planner reserves transfer, verification, cleanup and finalization inside the
same hosted-job allowance and charges every failed/interrupted native attempt
against the finite aggregate budget. It accounts for growth up to the original
work-tree ceiling, checkpoint bytes and a free-space reserve.

The proposed checkpoint transport admits predecessor plus successor only within
an explicit unpaid cache budget and observed headroom shared with ordinary CI.
It does not create cache entries, delete unrelated caches, change repository
quotas or assume a checkpoint fits. The carrier must bind the actual GitHub
service clock, current physical resources, source/image/package identities,
original variable capture, complete stopped process family and cache identities.
Planning records deliberately do not assess the origin of those observations.

The phase ledger reconciles the complete declared sequence only when every phase
record includes matching terminal, stamp inventory, quiescence and checkpoint
fields. These are reported values; the carrier must verify their provenance before
native qualification. JIT and main checks also require retained original test-report
evidence. Original upstream failures remain visible; reporting all original tests
green is not a substitute for retaining their actual outcomes.

Synthetic controls cover round trips and valid near misses, content/metadata/
predecessor changes, forged self-consistent caches, stale/missing checkpoints,
deadline and byte limits, late publication, failed attempts, skipped targets,
missing documentation/check dependencies and interrupted terminals. They execute
no upstream compiler or project source.
