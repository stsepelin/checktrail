# Bounded C/C++ native tools

The opt-in C17/C++20 build, CTest, clang-format and clang-tidy profile has required
native source and offline installed-package evidence. The
[measurement receipt](measurements/cpp-tools-native-2026-10-06.json) binds the
implementation, runtime, harness and controls. Broader E15 profiles and Gate A
remain open.

Select `cpp.build`, `cpp.ctest`, `cpp.clang-format` and `cpp.clang-tidy` in
`checktrail.json`. Declare scope in `checktrail.cpp-tools.json` using the published
[configuration schema](../schemas/cpp-tools-config.schema.json). The original
[example](../examples/cpp-tools) includes both configurations and the exact CMake
file for this profile. Existing `cpp.clang-check` retains its separate prepared
frontend contract in [CLANG.md](CLANG.md).

## Declared build scope

The measured profile uses Alpine Clang/LLVM 22.1.3, CMake/CTest 4.2.3, GNU Make
4.4.1 and Node 22.23.2 on `aarch64-alpine-linux-musl`. It accepts C17 `.c` and
C++20 `.cpp` sources, `.h`/`.hpp` headers, static libraries and executables.
Every inventoried source, header and `.h.in` template must be declared. Each
source belongs to one target. Static libraries require an executable consumer;
transitive library dependencies and repeated archive member basenames are unsupported.

Generated headers use explicit integer `CT_` variables and owned `generated/NAME.h`
outputs. `CMakeLists.txt` must exactly match the engine's finite renderer, including
standards, includes, target dependencies, generation, registered tests and timeouts.
Arbitrary CMake commands, external project dependencies, other source extensions,
platform variants and wider build options need separate profiles. Canonical ASCII
paths exclude whitespace, quotes, traversal and shell syntax. Planning reads data
without evaluating CMake or executing project code.

Execution requires operator trust at CLI invocation or MCP startup. A tool
argument cannot grant it. Fresh owned source, HOME, temporary and build directories
prevent reuse of project output. Compiler, linker, CMake, CTest and loader overrides
are protected; the compiler uses no default configuration or implicit modules.
The engine does not acquire dependencies or start infrastructure.

## Native participation

The validator reconciles CMake file-API codemodel and input metadata, every target,
compile group, include, dependency, artifact and compilation-database command.
Command strings are decoded as a restricted passive grammar and compared with
fixed expected argument arrays; they are never executed as shell commands.
Sequential verbose builds must account for every compile command and compiler
SARIF receipt. Compiler errors yield source findings rather than successful builds.

Raw object bytes and native DWARF file checksums bind project sources and consumed
headers. Generated bytes must match their template. Every static archive member
must equal its observed object. Link metadata, actual verbose commands and linked
executable symbols bind executable participation. Static linking may legitimately
select only some archive members: the archive covers all declared objects, while
executable symbols must cover its own primary sources and validate observed project
inputs. The union must account for all declared source, header and generated scope.
An unused declared header leaves execution incomplete.

SHA-256 identities bind original/copied inputs, artifacts and before/after native
tool entry bytes. DWARF's native MD5 checksums provide compiler participation under
trusted execution; they are not adversarial attestation. SDK files and the entire
system library closure are not individually bound by this profile. Receipt
coherence, fresh copies and container networking settings are not an OS sandbox.

## Tests, formatting and analysis

CTest's native JSON inventory must match every declared executable command,
working directory and timeout. Native backtraces bind each registration to the
physical `add_test` line. Console starts/results, global totals and JUnit counters
must agree. Empty, skipped, disabled, stale or incomplete collections cannot pass.
Counts describe CTest callbacks; assertions inside each executable remain unknown.
A test finding points at the CMake registration and explicitly does not identify
the failing assertion or establish a production mechanism, severity or remedy.

clang-format runs with an explicit owned style and XML replacement output. The
validator requires complete output, valid UTF-8 byte boundaries, non-overlapping
edits and one-pass XML entity decoding. A nonempty replacement set fails even
when native exit status is zero. It never rewrites source.

clang-tidy runs every declared translation unit with explicit configuration,
selected checks, warnings-as-errors and native YAML findings. The measured defect
and repair controls cover `bugprone-use-after-move` and
`clang-analyzer-core.DivideZero`. Enabling the division analyzer also enables its
required core checker set; native `--list-checks` must match that complete set.
The pinned core closure is recorded in the implementation and reconciled against
native output. This is consistent with Clang's
[analyzer check documentation](https://clang.llvm.org/docs/analyzer/checkers.html)
and [checker selection implementation](https://github.com/llvm/llvm-project/blob/main/clang-tools-extra/clang-tidy/ClangTidy.cpp).
Not every core checker has an individual defect fixture. Wider analyzer rules and
configurations remain unverified. Source suppression markers, including markers
inside literals, are unsupported rather than silently narrowing execution.

## Required acceptance and preparation

The `cpp-tools` required profile fixes original callback names. It requires native
build/compiler errors, CTest regression and repair, formatting and analyzer defect
and repair, metadata/scope/command/checksum/artifact guards, CLI/MCP trust and
privacy, concurrency, missing tools, protected settings, reached cancellation,
source changes and generated-header/executable changes. Every required callback
must pass without skips. Compiling mutation controls select one original callback
and require failure at its intended assertion; a setup or compilation error does
not count as a killed guard.

From a prepared ARM64 checkout, explicitly prepare and verify:

```sh
npm run build
CHECKTRAIL_TEST_TASK=original-cpp-task node scripts/prepare-cpp-tools-runtime.mjs
node scripts/prepare-package-cache.mjs
node scripts/verify-cpp-tools-container.mjs
```

The operator preparer uses an immutable Node image and checksum-pinned Alpine
packages. Normal APK signature verification remains enabled; the runtime build
uses networking disabled. `CHECKTRAIL_CPP_APK_DIRECTORY` selects exact already
acquired regular archives, and `CHECKTRAIL_CPP_BASE_PREPARED=1` uses an already
acquired immutable base. The local acceptance measured that prepared-archive path.
The preparer's default fetch path and the new hosted ARM64 job remain unverified
for this revision. Preparation refuses an existing destination or owned image tag.

Source acceptance and a fresh offline production installation use the same pinned
runtime with networking disabled, CPU/memory limits and readonly source/consumer
mounts. Lifecycle scripts are disabled; fixtures, official MCP client and acceptance
harness live outside the installed package. Container scratch remains writable.
On this Mac, agents use the shared foreground dev-env lifecycle. At task end stop
owned work, check status and run `node scripts/cleanup-cpp-tools-runtime.mjs`.
Cleanup checks ownership and refuses while an owned container remains; code and
acceptance artifacts are preserved.

No inference or real-project field evaluation is part of these controls. Windows,
other native targets/SDKs, wider CMake/frameworks, complete attempt archives,
publisher/license closure and representative-project performance remain open.
